Offline Melee policy experiments

This draft explains the path from controller data to action chunks. It separates controlled tests from historical tests. It uses closed-loop play as the main measure.

The audited run ledger and the machine-readable table are the source of truth. They contain 37 W&B runs.

0. Choose the evaluation metrics

No one metric is sufficient. Open-loop metrics measure imitation. Closed-loop metrics measure play.

Table 1. Metric choice
MetricQuestionWhy use it?Main limit
Validation NLLHow much probability does the policy give to the recorded action?It is a proper score. It uses the full predicted distribution. Lower is better.It uses recorded history and teacher forcing. It does not measure recovery from model errors.
Button or group accuracyDoes the most likely class match the recorded class?It is easy to read. It finds large decoding errors.Holds and neutral inputs are common. High accuracy can hide rare action errors.
Change-event F1Does the policy change a controller group when the player changes it?It gives more weight to rare transitions than raw accuracy.The current val/change_f1 covers all four groups. It is not a button-only F1.
Net damage LCBWhat lower bound do we have on damage dealt minus damage taken?Damage is dense. It reacts before stock results become stable. Higher is better.Damage is not the win condition. A policy can deal damage and fail to take a stock.
Net stock LCBWhat lower bound do we have on stocks taken minus stocks lost?Stocks are close to the game objective. The lower bound penalizes noisy results. Higher is better.Stocks are sparse. The estimate needs many boots and one fixed protocol.
Use this order. Use net stock LCB as the main score. Use net damage LCB as the second score. Use NLL, accuracy, and F1 to diagnose the model.
Do not call codec reconstruction a policy score. Old fields such as recon_f1 and recon_acc test quantization and reconstruction. For current models, use val/acc_o01_buttons, val/change_f1, val/exact_frame_acc, and val/dense_prefix_h4_acc.

The repository LCB is a conservative one-sided 95% lower bound. It uses the confidence intervals for the positive and negative rates. It is not the low end of a two-sided interval for the net value. Always report the point estimate, LCB, boots, matches, crashes, and protocol.

NLL values in this report are in bits per frame unless the table says otherwise. Compare NLL only when the action vocabulary, offsets, and loss aggregation match. PF means approximate training petaflops. The estimate is 6 × parameters × processed training positions.

1. Encode the controller

Keep simultaneous button presses

The early 2025 system reduced simultaneous button presses to one label. This removed information from the replay.

Old: eight button bits→select one active button→one label
Current: A, B, X, Y, Z, R, L, D-up→eight-bit mask→one of 28 = 256 combinations

The current format preserves jump-and-attack inputs and other same-frame combinations. It also models the complete button chord with one categorical distribution. The cost is a larger and sparse output vocabulary. This choice can hurt a small model. We accept that cost because the target must keep the original action.

Design choice. We do not have a clean small-scale result for the 9-class and 256-class button formats. This section makes a data-fidelity argument. It does not make a performance claim.

Use more analog detail

Learn how each controller group enters the model

In 026, buttons use their eight bits as physical values. Sticks use their two coordinates. Triggers use their two levels. Each group also has its own learned class table. The separate modules give the model the group role. There is no extra role vector.

Experiment 028 keeps the same analog classes. It removes the learned and semantic controller codec. Thus, 028 tests the input encoding. It does not test analog resolution.

One RLE representation failed

Experiment 018 used BPE/RLE action tokens. Run xgj1dwot had stock LCB -3.5838 and damage LCB -169.7728. It also had a 57.7% crash fraction. The output format, execution timing, parameters, and training PF changed. This result rejects that tested RLE system. It does not reject all RLE systems.

2. Factor the action decoder

MTP means multi-token prediction. One frame context predicts actions at several future frame offsets. AR means autoregressive. A later prediction reads an earlier prediction.

The decoder changed in two steps. First, it predicted more future frames. Then it made later predictions depend on earlier predictions. “DSV3-style” is the name used here for the small causal decoder over selected offsets. It is a design label. It does not mean that this code is an exact copy of DeepSeek-V3.

game state + controller history→causal frame trunk→future offset 1→future offset 2→future offset 3→future offset 4→execute four frames→replan
future-frame state→C-stick→main stick→triggers→buttons

Principal MTP architectures

D0 is a matched information-flow control. It is not the old 016 implementation. D0 keeps the complete 037 temporal decoder and its parameter count. A diagonal attention mask removes future-to-future information. Every offset reads the observed action again. This makes D0 comparable with D1, D2, and D3.

Two decoder questions remain

Group order. The current order is C-stick, main stick, triggers, buttons. There is no clean order test. Experiment 010 and experiment 019 use other orders, but many other settings also change. A useful one-run test changes only the order to main stick, C-stick, triggers, buttons. Triggers must remain before buttons because the legality mask uses the trigger result.

Interleaved tokens. The historical short-context 013 model places one state token and four action-group tokens in the main trunk for every frame. Its new 026-style evaluation has stock LCB -0.2442 and damage LCB +20.2728. This is close to D3. However, its token count, context, checkpoint step, training PF, and inference path differ. Keep it as a side branch. Do not place it in the D0-to-D3 causal chain.

3. Add offline RL

Monte-Carlo AWR uses the return from the recorded episode. It does not bootstrap through a learned Q function.

recorded return Gt+1−value V(ht)→detached advantage→capped exponential weight→weighted imitation loss

Experiment 036 uses beta = 0.8, a raw weight cap of 5, and a 2,048-step BC warm-up. It weights the first four offsets. The value head fits the recorded return. Its value loss does not update the policy trunk.

The reward is stock change plus 0.01 times net damage change plus a 0.5 bonus for the game-ending stock. The discount is 0.99827.

5. Revisit flow matching

The first continuous flow model was a separate system. Experiment 001 used a 16-frame continuous chunk, eight flow steps, 4.994M parameters, and 546.9 PF. Its mean stock result was -2.262 per minute. Its mean damage result was -112.129 per minute. It had no confidence interval. This test changed too many settings to compare with D3.

Experiment 038 is a more useful test. It keeps the d256 trunk, controller codec, data, batch, updates, examples, offsets, H4 execution, and 96-boot protocol from experiment 037. It replaces the AR decoder with a categorical endpoint flow.

state and controller history→d256 causal trunk→noisy ten-offset action plan→bidirectional flow expert × 4→group argmax→execute offsets 1 to 4→replan
